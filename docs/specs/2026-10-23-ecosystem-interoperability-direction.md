# 下下阶段方向：复用现成互通能力

- 日期：2026-10-23。
- 状态：**Proposed — 研究后的交付方向，尚非已实现能力，也不是可直接执行的完整工程计划。**
- 用户要求：打通包括但不限于 DeepSeek Harness Desktop、ZCode、WorkBuddy；“打通本身”也先找 GitHub 开源项目，如 CC Switch，避免反复造轮子。
- 来源：根计划 §4.12–4.16、§20，`docs/research/2026-10-23-interop-reuse-review.md`。

## 目的

让用户在 HarnessHub 中找到已有工具、进入其配置管理、选择可用运行入口，并保留一致的项目/会话索引。
配置管理、Agent 协议、会话历史各自使用已有成熟实现；新增的只是必要的对接和可信状态显示。
客户端名单开放，新接点按同一验收标准加入，而不预先承诺所有客户端支持所有方向。

## 阶段顺序

1. 当前阶段：只读 Git 快照采集器（已另立 spec/plan）。
2. 下一阶段：Session 起止快照、持久化、历史展示；另定比较基准与失败语义。
3. 下下阶段：按下面的小成果复用既有工具，先验证底座，再扩产品覆盖。

本方向不改变现有 v0.1 release gate，也不因研究通过就勾选实际支持能力。
Git 第二阶段与 Packaging/跨平台验收仍需各自证据。

## 方案比较

| 方案                                              | 收益                                         | 代价                                    | 判断                       |
| ------------------------------------------------- | -------------------------------------------- | --------------------------------------- | -------------------------- |
| 外部应用/现成 CLI + 官方 ACP client，Hub 做薄适配 | 最大程度保留成熟配置投影、会话控制和维护责任 | 需核实版本、授权、回执与平台差异        | **优先验证**               |
| 提取 MIT/Apache 小模块，固定版本 vendor           | 没有稳定外部 API 时可保留必要功能            | 要维护 fork、许可/依赖、schema 漂移     | 接口验证失败后再逐模块论证 |
| 自建统一配置、协议和队列框架                      | 可完全控制界面                               | 重复已有能力，新增 ownership 和兼容负担 | 本方向不采用               |

“优先验证”不等于强制采用特定依赖。若上游无法满足只读/回执/平台要求，先提改进或换已有工具；不要立刻重写。

## 交付切片与可核验成果

### C0：隔离互操作试验，先做采用决策

- 固定 CC Switch GUI/CLI、acpx 和官方 ACP Agent 版本/许可；不执行自动安装脚本。
- 使用唯一测试目录，分别隔离 GUI/CLI 配置，不改真实 HOME、凭证和 Session。
- CC Switch 无凭证 MCP/Skill 样例：打开确认、导入、已支持客户端配置输出、取消、冲突、回滚；核对究竟能读回哪些状态。
- CLI 先用假配置验证 list/current 的输出与副作用、switch/start 的范围和退出码；不采集真实 secret 输出。
- 假 ACP Agent 验证 initialize/new/events/cancel/close/resume、失败恢复、双客户端共享 owner；不请求云模型。
- 产出采用/不采用表及具体接口缺口，优先向上游补脱敏 JSON、操作 ID、状态读回。

**验收：** 有可重放 fixture 和实际命令记录，明确对接方式；无 Hub 新配置同步引擎、无写上游私有 DB。

### C1：复用配置管理入口

- 发现已安装 CC Switch / 选定 CLI，显示版本和经验证的作用域；用户选择后打开原管理面或执行受支持命令。
- 不在 Hub 重做 Provider/MCP/Skills 表单与格式投影；缺客户端格式优先贡献上游。
- 只保存外部工具 ID/版本/操作引用；上游拥有其配置、备份、回滚和 Secret。
- 无回执时显示“已请求打开确认”；有结构化结果并 readback 后才能显示“已激活”。
- 每个配置目标只选一个写入所有者。检测到 ownership 不明/运行中不热加载时，明确需要用户在原工具完成操作。

**验收：** 同一个无凭证配置从 Hub 入口经现成工具到一个实际支持客户端，全链路结果可查；取消和失败不显示成功；无密钥进入 URI、SQLite 或日志。

### C2：复用 Agent 协议与会话控制

- 首选固定本地 acpx executable/runtime；必要时采用官方 ACP SDK，而非手写协议栈。
- 先接官方 DSH ACP；Codex/Claude/Gemini/OpenCode 已有 ACP 映射可以作为回归覆盖。
- 统一 Hub/source session ID 映射和只读投影，不写 acpx/外部客户端的 session store。
- 明确 CLI 与 shared runtime 的新建/恢复失败语义、关闭客户端与关闭 owner 的区别。
- 进程控制只有一个所有者；外部 runtime 自己持有的 owner 不冒充本仓 PTY 子进程。
- 现有 HarnessAdapter、UsageSourceAdapter、插件协议和能力矩阵保持各自边界。需要扩展冻结接口时先新增 ADR。

**验收：** 两个实际 Agent 使用本地模型或本机 mock endpoint，通过同一现成客户端完成隔离任务、事件、取消、错误、重启恢复；不发送原文到云端。Windows 进程回收与不重复 owner 有实际证据；未验证的 resume/usage 等能力为 false。

### C3：桌面与更多产品覆盖

- DSH Desktop：区分官方 runtime、Dataelem Electron、社区 Tauri；已运行桌面的 Gateway/SessionControl 需单独验证稳定入口、授权、baseline/seq、重连。
- ZCode：优先官方 CLI 检测/启动与格式贡献，版本和路径 fixture 先行；配置 GLM 不等于接通 ZCode。
- WorkBuddy：先区分桌面、CodeBuddy CLI、官方云任务与 MCP/Skill 消费方向；不以第三方包装器名称替代证据。
- 其他工具通过同一套“复用底座 + 薄适配 + 独立验收”加入，不按产品各造一个配置与调度系统。

**验收：** 每个产品列出检测、打开 GUI、配置、发任务、取消、恢复、历史、用量的实际状态；不把“能打开 GUI”“支持 MCP”“能发 HTTP”当作全部贯通。

## 当前硬边界

- 外部日志和 Session 数据只读；不迁移/删除上游历史，不通过账号切换工具改认证文件。
- Prompt/Response/Session 原文不得发往网络；WorkBuddy 云 API 仅作已发现接口记录，默认路线不调用。若以后明确要云模式，必须先调整规则和 runtime target 规格。
- Secret 留在原工具/OS 凭证库；Hub 只有 credential_ref，不复制、不通过深链传递。
- ACP 不是 MCP，现有插件 JSON-RPC 也不是二者的通用兼容层。
- 许可不清、要求非标准附加条件的代码暂不复制；已有代理、模型路由和队列不另造等价实现。
- 不因为本提案新增全局代理、账号池、第二套 SQLite 或云同步后台。

## 进入实现前需要锁定的决策

C0 先给出实际试验结果，再锁定配置所有者（GUI 或 CLI）、ACP 对接方式（外部进程或库）、成功回执、Windows 支持和错误语义。
每个可测试切片形成独立 spec/plan、TDD、小提交与 PR。
当前提案只确定复用优先级、交付顺序和验收问题，不提前冻结尚未验证的接口或虚构实现文件。
